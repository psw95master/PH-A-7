### 2. 리뉴얼 방향 3안 확정

페리 초안(2안)에 **3안(단계 개편)**을 추가했다.

| 안 | 명칭 | 내용 |
| --- | --- | --- |
| 1안 | 기능 개편 | 보이는 화면 유지 + 작동 방식 전면 재구축 |
| 2안 | 전면 개편 | 화면 + 작동 방식 함께 신규 |
| 3안 | 단계 개편 | 기능 먼저, 화면은 성과 확인 후 |

> ⚠️ **초안 1안 정의를 수정했다.** 초안은 「현재 웹사이트에서 이미지 텍스트를 html로」였는데, 이는 기존 코드 유지 = 부분 수정으로 읽힌다. 현행 사이트는 프레임 2개 · 1200px 고정이라 **부분 수정으로는 휴대폰 대응 불가**이며, S9에서 「부분 수리로는 해결되지 않습니다」라고 진단해 놓고 1안으로 부분 수리를 파는 **자기모순**이 된다. → 「보이는 인상은 유지, 속은 전부 신규 제작」으로 재정의.

- **판단 축도 바꿨다.** 초안은 「비용·기간 vs 시각효과」였고, 이 축이면 대표는 자동으로 1안을 고른다. 제안서 목적(채용)과 무관한 기준이다. → **「대상별 판단 방식 차이」**로 교체 (거래처는 정보를 읽고 판단 / 구직자는 첫인상으로 판단).
- **촬영비는 2안 단점에서 빼서 견적의 「선택」 항목으로 분리**했다. 촬영은 디자인 방향이 아니라 콘텐츠 범위 결정이다. **콘텐츠 작성비**(설비명·규격·실적 목록·인증·연혁)는 어느 안이든 발생하는데 초안 두 안 모두 누락되어 있어 공통 범위에 명시했다.

> ⚠️ **3안은 최종 덱에 남지 않았다.** v1.0 최종본(03-2)은 **1안 기능 개편 / 2안 전면 개편** 두 가지만 제시한다.

### 3. 수치 정정 2건 — 둘 다 재현 불가였다

#### ① 검색 텍스트 「97자」 → **57자**

원 출처는 ESL-C-3 v1.0의 「58자(프레임 합산 97자)」인데 **측정 과정이 남아 있지 않았다.** 직접 재측정한 결과:

| 항목 | 값 |
| --- | --- |
| 조각 1 `music.htm` | **404 — 파일 없음** |
| 조각 2 `main/index.htm` | 표시 텍스트 **57자** |
| 이미지 | **14개** (원 진단서 12개) |
| 이미지 설명(alt) | **0개** |
| 내부 페이지 제목 | `Untitled Document` |

「97자」는 두 조각 합산치인데 한 조각이 404라 재현되지 않는다. 발표 중 확인 요청을 받으면 방어 불가.

- **표기 원칙** — 숫자를 크게 띄우는 자리는 **「회사 정보 0자」**를 쓴다. 57자도 회사 설명이 아니라 16년 전 공지 두 줄이다.

#### ② 「동종 6개사 중 견적 폼 2곳」 → **7개사 중 6곳** (사실과 반대)

ESL-C-7 기재 수치인데 **조사 대상 목록과 URL이 없어 대조 불가**였다. 직접 실측:

| 업체 | 보안 | 휴대폰 | 문의창구 |
| --- | :-: | :-: | --- |
| 진양유압 | ○ | ○ | ○ 견적문의 전용 |
| HIMC | ○ | ○ | ○ |
| 태광유압 | ○ | ○ | ○ |
| BB하이드롤릭 | ○ | ○ | ○ |
| ISTC | ✕ | ✕ | ○ 견적/발주 전용 |
| 태산유압 | ✕ | ✕ | ○ 온라인문의 |
| 삼익유공압 | ✕ | ✕ | △ 게시판만 |
| **나우하이텍** | ✕ | ✕ | ✕ |

- **판정 기준** — 「보유」는 이름·전화 안내가 아니라 **실제 `<form>`과 입력칸이 있어 웹에서 바로 보낼 수 있는 경우**만.

**기타 발견**

### 4. 메인 시안 2종 제작 (HTML)

- **형식을 HTML로 택한 이유** — 창 폭을 좁히면 화면이 따라 줄어드는 것을 **실물로 보여줄 수 있다.** 현행 사이트는 아무리 좁혀도 줄지 않으므로, 두 화면을 나란히 놓고 창을 좁히면 「휴대폰 대응」을 말로 설명할 필요가 없다.
- **사진은 나우하이텍 현행 사이트에서 추출**했다. 외부 스톡을 쓰면 "우리 회사 같지 않다"가 된다.

| 원본 | 잘라낸 것 |
| --- | --- |
| `nawoohitech.co.kr/images/sub/contents7_01.jpg` | 제품 (댐 수문 실린더 · 2,300톤 밸런스 실린더 등) |
| `nawoohitech.co.kr/images/sub/contents5.jpg` | 설비 (대형 선반 · 머시닝센터 · 천장 크레인) |

> 두 원본 모두 **페이지 전체가 이미지 한 장**이다. 진단서의 「회사 정보 전량이 그림 파일」이 문자 그대로 사실임을 확인.

- **설비명은 육안 판단이다.** 원본에 설비명이 없어 사진을 보고 붙였다. 규격은 모르므로 넣지 않았다. 발표에서 대표가 "이름이 틀렸다"고 하면 **오히려 진단을 증명하는 답**이 된다.
- **수정한 버그 2건**
  - 한글이 단어 중간에서 끊김 → `word-break: keep-all` 전역 적용
  - 1안 모바일에서 로고 3줄 깨짐 + 메뉴 버튼이 화면 폭 전체로 늘어남 → 전역 `button{width:100%}`가 햄버거에도 걸린 것. `form button`으로 한정

### 6. 구글 슬라이드 변환 — 업로드가 막힌 진짜 원인

스크립트 v2.5를 python-pptx로 15장 PPTX로 생성했다. **본문은 슬라이드에, 화면 요소와 발표 멘트는 발표자 노트로** 분리.

```bash
scratchpad/build_deck.py   # python-pptx 1.0.2, venv 필요
```

**드라이브 업로드 실패 4회와 각 원인**

| 시도 | 실패 원인 |
| --- | --- |
| 파일 입력 요소 찾기 | 드라이브는 업로드 버튼을 누르기 전엔 `input[type=file]`을 만들지 않음 |
| JS 합성 드래그앤드롭 (2회) | 브라우저가 `isTrusted=false`로 표시 → 드라이브가 무시 |
| 업로드 버튼 클릭 | **맥 파일 선택창** — 브라우저 바깥이라 조작 불가 |
| MCP 연결기 base64 전송 | 파일 89KB → base64 **118,896자**. Read 도구 상한(약 20,000자)의 6배 |

> 🔑 **당시 결론 — 드라이브 업로드는 반드시 맥의 파일 선택창을 거친다.** System Events(맥 조작) 권한을 페리가 허용하면서 경로가 열렸으나, 실제 업로드는 페리가 직접 수행했다.
>
> ⚠️ **이 결론은 브라우저 조작 경로에 한정된 이야기였다.** 다음 날 **드라이브 API로 업로드하면서 변환**하면 브라우저·파일 선택창 없이 네이티브 구글 슬라이드가 된다는 것을 확인했다. [[PH-A-7_log_260807]]
>
> ⚠️ 나아가 260815에는 **PPTX 변환 자체가 불필요**해졌다. `~/apps/gdocs/token.json` 의 `drive` 스코프로 **Slides API 직접 호출**이 통과한다. [[PH-A-7_log_260817]]

파일 크기 축소는 무의미했다. 노트를 발표 멘트만 남겨도 89KB → 86KB (압축 때문). **빈 슬라이드 1장짜리 PPTX도 이미 28KB**라 python-pptx 기본 템플릿 자체가 하한이다.
