세션 도중 페리가 범위를 **「인터넷에서 홈페이지가 정상적으로 나오는지」** 로 좁혔다.

## 1. 🔴 원인 규명 — KT 이름서버 클러스터의 일부 노드

`dig` 을 리졸버별로 찍어 갈랐다. 여기서 바로 드러났다.

| 조회 경로 | 결과 (`260923 08:50`) |
| --- | --- |
| Cloudflare 권위 서버 (`celine`·`garret`) | ✅ 새 사이트 IP |
| `1.1.1.1` · `8.8.8.8` | ✅ 새 사이트 IP |
| `.co.kr` 상위 존 위임 | ✅ Cloudflare |
| **KT (`168.126.63.1`) — 8회 반복** | ❌ **2회가 옛 IP `211.51.221.181`** |

### 왜 「왔다갔다」 했는가

KT 이름서버는 한 대가 아니라 **여러 대가 묶인 클러스터**다.
그중 일부만 옛 값을 들고 있어서, **같은 기기가 같은 주소를 쳐도 어느 노드에 걸리느냐에 따라**
새 사이트가 나왔다 옛 사이트가 나왔다 했다. 약 4번에 1번꼴이었다.

`260922` 로그의 「같은 PC 에서 한 번 정상이었다가 다시 옛 서버로 돌아갔다」가 정확히 이것이다.
캐시가 자연히 풀리는 방향과 반대로 보였던 것은, 풀린 노드와 안 풀린 노드가 섞여 있었기 때문이다.

### 🔴 `260922` 안내 정정

> 「컴퓨터를 껐다 켜면 된다」 → **이 건에는 듣지 않는다.**

기기가 아니라 **통신사 서버**에 남은 기록이라, 방문자 기기에서 할 수 있는 일이 없었다.
`260922` 로그의 회사 안내 문구(「컴퓨터를 한 번 재시작」)는 이 건에 대해 철회한다.

### 하루 동안의 소멸 경과 — 저절로 풀렸다

옛 A 레코드의 유효기간이 `86400`(24시간)이고 전환이 `260922 19:30` 이었으니,
`260923 19:30` 경 소멸이 예상됐고 실제로 그렇게 됐다.

| 측정 시각 | 옛 서버 응답 |

| `08:50` | 2 / 8 회 (25%) |

## 2. 파비콘 추가 — 구글에 지구본이 뜨던 이유

페리가 구글 검색 결과 화면을 캡쳐해 **사이트 이름 옆 동그란 자리**를 지목했다.

### 원인

**사이트에 파비콘이 아예 없었다.** 선언(`<link rel="icon">`)도 파일도 `0`건.
그래서 구글이 기본 지구본 아이콘을 채워 넣고 있었다.

### 심볼만 잘라 쓴 이유

로고 원본(`assets/img/logo.png`)이 **192×48 가로형**이다.
정사각형 파비콘에 통째로 넣으면 16px 화면에서 글자가 뭉개진다.
페리도 같은 판단으로 심볼 이미지를 따로 보내왔다.

로고를 픽셀 단위로 훑어 심볼 경계를 쟀더니 **정확히 `x=2~45` · `y=2~45`** 였다.
44×44 정사각형에 사방 2px 여백. `0~48` 로 자르면 중앙 정렬로 딱 떨어졌다.

- `sips` 로 먼저 시도했으나 **중앙을 잘라서 글자 부분이 나왔다.** (`--cropOffset` 이 중앙 기준)
- 표준 라이브러리(`zlib`·`struct`)만으로 PNG 디코더·인코더를 써서 직접 잘랐다. 외부 패키지 0개.
- 자른 뒤 잉크 경계를 재검증해 `x=2~45 · y=2~45` 가 보존된 것을 확인했다.

### 결과

| 항목 | 값 |
| --- | --- |
| 파일 | `PH-B-35/assets/img/favicon.png` (48×48, 2,305 bytes) |
| 선언 | 전 페이지 `<head>` — **14개** |
| 제외 | `notice.html`·`qna.html` — 0초 리다이렉트 + `noindex` 라 의미 없음 |
| 커밋 | `fee1fbe` · 배포 반영 15초 |

### 구글 검색 결과에는 바로 안 바뀐다

구글 공식 문서 기준 **재크롤링에 수일~수 주**. 그래서 서치콘솔 등록(아래 6번)이 급해졌다.

> 참고 — 구글 요구사항은 **정사각형 / 최소 8×8 / 48보다 크면 권장 / 크롤러 차단 없을 것**.
> 로고 원본이 저해상도라 48×48 이 한계다. 업스케일은 흐려지기만 해서 하지 않았다.
> 더 큰 아이콘이 필요하면 **회사 로고의 벡터·고해상도 원본**을 받아야 한다.

## 4. 🔴 옛 주소 `/index.htm` 이 404 였다

전체 페이지를 훑다가 발견했다. 리다이렉트 목록에서 **빠져 있던 주소**다.

옛 서버가 아직 살아 있어서(`260927` 해지 전) 직접 물어 확인했다.

```
옛 서버 /index.htm      → 200   (루트와 같은 frameset 화면)
새 사이트 /index.htm    → 404   ❌
```

옛 홈이 링크한 것은 `main/index.htm` 과 `music.htm` 둘뿐이었고, 루트 레벨에서 살아 있는
주소는 `/index.htm` 하나였다. 구글에 이 주소가 색인돼 있으면 방문자가 404를 본다.

`OLD_PATHS` 에 추가했다 (`ca6ce9a`). 반영 후 재검증 — **옛 주소 5종 전부 홈으로 301.**

```
/index.htm  /main/*  /bbs/*  /music.htm  /css/*   →  /  301
```

> 이 문자열은 `l`(엘)과 `I`(아이)가 섞여 있다. 화면 글꼴로는 구분이 안 돼서,

## 7. 작업 중 겪은 것 — `www` 실패는 작업 기기 문제였다

최종 점검에서 `https://www.nawoohitech.co.kr` 이 5회 연속 `000`(연결 실패)로 나왔다.
**전환이 깨진 줄 알고 한 번 긴장했는데, 작업 기기만의 문제였다.**

```
dig (KT·CF·Google, 각 12회)        →  전부 Cloudflare IP   ✅
dscacheutil / getaddrinfo (macOS)  →  211.51.221.181       ❌
```

`dig` 은 DNS 서버에 직접 묻고, `curl` 은 **macOS 시스템 리졸버**를 거친다.
그 층에만 `www` 의 옛 값이 남아 있었다 (`apex` 는 이미 갱신돼 있었다).

캐시를 우회해 확인하니 정상이었다.

```
--resolve www…:443:104.21.47.243   →  200 · 새 사이트
인증서 CN = www.nawoohitech.co.kr  ·  Google Trust Services  ·  ~2026-12-21
```

> **교훈 — `dig` 이 정상인데 접속이 안 되면 기기의 시스템 캐시를 의심한다.**
> `260922` 의 페리 PC 403 도 같은 층위였을 가능성이 크다.
> `sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder`
